# Migrating from pgserve 2.5 → 2.6

This guide covers what changed between `pgserve@2.5.0` and the `pgserve@2.6.x`
cohort, what action operators take during the upgrade, and how to roll back.

## TL;DR

- **No breaking changes** to existing `pgserve` invocations.
- Five new CLI verbs land: `doctor`, `trust`, `gc`, `provision`, `create-app`.
- One new schema (`autopg_meta`) and one new on-disk root (`~/.autopg/<slug>/`)
  appear after first `autopg create-app` invocation.
- Roll back by reinstalling the prior version — no destructive schema changes
  to existing databases.

## What changed

### New verbs

| Verb | Purpose |
|------|---------|
| `autopg doctor` | Read-only health probe for postmaster, pm2 supervision, on-disk roots, and trust store. JSON output via `--json`. |
| `autopg trust add\|list\|remove` | Manage `~/.pgserve/trust/identities.json` — operator-extensible cosign trust roots layered on top of the built-in `TRUSTED_IDENTITIES`. |
| `autopg gc [--dry-run\|--apply]` | Sweep orphan databases (rows in `pgserve_meta` whose source path no longer exists). Audit log at `~/.pgserve/audit/gc-<DATE>.log`. |
| `autopg provision <fingerprint>` | Idempotent DB + role provisioning for an app fingerprint. Writes a `pgserve_meta` row. Concurrency-safe via `pg_advisory_lock`. |
| `autopg create-app <slug>` | Per-consumer app registration: writes `~/.autopg/<slug>/admin.json` + sibling `manifest.json`, registers in `autopg_meta`, **freezes** the cosign trust roots for this consumer at create time (manifest LOCK 1). |

### New schema

`autopg_meta` (separate table from existing `pgserve_meta`):

| Column | Type | Purpose |
|--------|------|---------|
| `slug` | text PRIMARY KEY | sanitized app slug (e.g. `@demo/app` → `demo_app`) |
| `manifest_path` | text NOT NULL | absolute path to `~/.autopg/<slug>/manifest.json` |
| `locked_roots` | jsonb NOT NULL | snapshot of `TRUSTED_IDENTITIES` at create time |
| `created_at` | timestamptz NOT NULL DEFAULT now() | when the consumer was registered |
| `last_updated` | timestamptz NOT NULL DEFAULT now() | bumped on idempotent re-runs |

Bootstrap is automatic the first time `autopg create-app` runs against a host.
See [`docs/pgserve-meta.md`](../pgserve-meta.md) for the existing `pgserve_meta`
schema reference (different lifecycle: per-fingerprint database vs
per-consumer-app).

### New on-disk roots

| Path | Owner | Lifecycle |
|------|-------|-----------|
| `~/.autopg/<slug>/admin.json` | `autopg create-app` | per-consumer state file (mode 0600, dir 0700) |
| `~/.autopg/<slug>/manifest.json` | `autopg create-app` | sibling of admin.json — pinned schema `{schemaVersion:1, slug, lockedRoots, createdAt, lastUpdated}` |
| `~/.pgserve/trust/identities.json` | `autopg trust` | operator-extensible trust roots layered on `TRUSTED_IDENTITIES` |
| `~/.pgserve/audit/gc-<YYYY-MM-DD>.log` | `autopg gc` | one-line-per-event audit log; rotated by gc when >90 days old |

The host-level `~/.autopg/admin.json` (owned by `canonical-pgserve-pm2-supervision`
G1, supervisor-mode tracking) is NOT touched by this cohort. Per-consumer state
lives one directory level deeper (`~/.autopg/<slug>/admin.json`) — paths never
collide.

### Changed behavior

- **`autopg install --help`** — now respects `--help`/`-h` and exits 0 without
  performing the install. Previously `--help` was ignored and the install ran.
- **`autopg install` port pre-flight** — refuses to start if port 5432 is
  already in use (IPv4 + IPv6 connect probe). Prevents the silent failure mode
  where pm2 reports `online` while postgres has crashed.
- **Unknown verbs** — `pgserve foo` now exits non-zero with an "unknown verb"
  error. Previously it printed top-level help and exited 0.
- **`autopg doctor`** — surfaces missing `pgaudit` extension as a non-PASS
  finding (was silently fall-through).
- **`autopg config --help`** — exits 0 with a usage block (was running the
  config logic against `--help` as if it were a key).

## Action checklist for operators

For most consumers, **no action is required** — existing `pgserve` invocations
continue to work unchanged.

If you want to opt into the new surface:

1. **Install or update via the canonical installer** (cosign-verified GitHub
   Releases tarball):
   ```bash
   curl -fsSL https://raw.githubusercontent.com/automagik-dev/autopg/main/install.sh | bash
   # Pin a specific version:
   PGSERVE_VERSION=v2.6.1 curl -fsSL https://raw.githubusercontent.com/automagik-dev/autopg/main/install.sh | bash
   # Dry-run (print actions without executing):
   bash install.sh --dry-run
   ```
   The installer fetches the per-platform tarball from
   `github.com/automagik-dev/autopg/releases/download/v<version>/`, verifies
   the cosign attestation via `gh attestation verify`, then runs
   `autopg install` to wire pm2 supervision.

2. **Verify the install**:
   ```bash
   autopg doctor --json
   ```
   Every check should report `PASS` or `WARN` — zero `FAIL`. If a check fails,
   the JSON output describes the remediation.

3. **(Optional) Register your app for manifest LOCK 1**:
   ```bash
   autopg create-app @your-org/your-app
   ```
   This freezes the cosign trust roots for your app at the moment of creation.
   Subsequent `pgserve upgrade` invocations against your binary verify against
   the frozen roots, not whatever `TRUSTED_IDENTITIES` is at upgrade time.
   See [`docs/pgserve-meta.md`](../pgserve-meta.md) for schema details.

4. **(Optional) Add a custom trust root**:
   ```bash
   autopg trust add my-org-release \
       --issuer https://token.actions.githubusercontent.com \
       --identity-regexp '^https://github.com/my-org/my-app/.github/workflows/release.yml@refs/tags/v.*$' \
       --publisher '@my-org/my-app' \
       --description 'My organization release pipeline'
   autopg trust list
   ```
   See [`docs/trust-store.md`](../trust-store.md) for the full CLI reference
   and the precedence rules between built-in and user-extensible roots.

## What NOT to change

- **Do not edit `~/.autopg/<slug>/admin.json` or `manifest.json` by hand.**
  The authoritative source is `autopg_meta`; cache files are derived. If they
  drift, `autopg doctor` reports the divergence and you can `rm -rf` the
  consumer dir + re-run `autopg create-app <slug>` to rebuild from the table.
- **Do not edit `pgserve_meta` rows directly.** Use `autopg provision` /
  `autopg gc` — they handle the advisory-lock + audit-log invariants.
- **Do not replace `~/.pgserve/trust/identities.json` wholesale.** Use
  `autopg trust add/remove`. The format is documented in
  [`docs/trust-store.md`](../trust-store.md); the verbs ensure schema
  validity + hardcoded-id shadow refusal.

## Rollback

`pgserve` 2.6.x does not perform any destructive schema changes against
`pgserve_meta` (existing column shape is preserved; `autopg_meta` is purely
additive). To roll back, re-run the installer with a pinned older version:

```bash
PGSERVE_VERSION=v2.5.0 curl -fsSL https://raw.githubusercontent.com/automagik-dev/autopg/main/install.sh | bash
# Or any prior pin you had verified.
```

The new `~/.autopg/<slug>/` directories and `~/.pgserve/trust/identities.json`
are left in place but become inert (older versions don't read them). To purge:

```bash
rm -rf ~/.autopg/<slug>/
rm -rf ~/.pgserve/trust/
# autopg_meta rows persist — drop manually if desired:
psql -d postgres -c "DROP TABLE IF EXISTS public.autopg_meta;"
```
