# pgserve trust store

This is the operator reference for `~/.pgserve/trust/identities.json` — the
user-extensible cosign trust store layered on top of pgserve's hardcoded
`TRUSTED_IDENTITIES`. Trust store changes are made through `pgserve trust
add|list|remove`; the JSON file is a derived artifact of those verbs.

## Concept

pgserve's binary-verification path checks a candidate cosign attestation
against a list of trusted identities. There are **two layers**:

| Layer | Source | Mutability | Lifecycle |
|-------|--------|------------|-----------|
| Hardcoded | `src/cosign/trust-list.js` (`TRUSTED_IDENTITIES`) | frozen at build time | updated by shipping a new pgserve binary |
| User-extensible | `~/.pgserve/trust/identities.json` | mutable via `pgserve trust add`/`remove` | persists across pgserve upgrades on the host |

A binary verifies if **either** layer matches. Operators cannot remove
hardcoded entries (they're frozen `Object.freeze` in the source); `pgserve
trust remove <id>` against a hardcoded id refuses with exit 1.

## Built-in `TRUSTED_IDENTITIES`

As of pgserve 2.6.x, three identities ship hardcoded:

| `id` | `publisher` | matches workflow |
|------|-------------|------------------|
| `automagik-genie-release` | `@automagik/genie` | `automagik-dev/genie` `release.yml@refs/tags/v.*` |
| `automagik-omni-release` | `@automagik/omni` | `automagik-dev/omni` `release.yml@refs/tags/v.*` |
| `automagik-pgserve-release` | `pgserve` | `namastexlabs/pgserve` `release.yml@refs/tags/v.*` |

All three pin the Sigstore GitHub Actions OIDC issuer
(`https://token.actions.githubusercontent.com`) and tag-triggered release
workflows. Verification examples in
[`docs/migrations/v2.6-from-v2.5.md`](migrations/v2.6-from-v2.5.md).

## File location and format

```text
~/.pgserve/trust/identities.json
```

Mode `0600` (operator-only read/write). The directory `~/.pgserve/trust/`
is mode `0700`. Both are created lazily on first `pgserve trust add`.

Schema (one entry per array element):

```json
{
  "schemaVersion": 1,
  "identities": [
    {
      "id": "my-org-release",
      "publisher": "@my-org/cli",
      "issuer": "https://token.actions.githubusercontent.com",
      "identityRegexp": "^https://github.com/my-org/cli/.github/workflows/release.yml@refs/tags/v.*$",
      "description": "My private release pipeline",
      "addedAt": "2026-05-10T18:23:11.000Z"
    }
  ]
}
```

| Field | Required | Purpose |
|-------|----------|---------|
| `id` | ✅ | short stable identifier; collides with hardcoded ids = refuse |
| `publisher` | optional | `package.json` `pgserve.publisher` value the entry attests |
| `issuer` | ✅ | OIDC issuer URL (matches `cosign verify --certificate-oidc-issuer`) |
| `identityRegexp` | ✅ | `cosign verify --certificate-identity-regexp` value (anchor with `^…$`) |
| `description` | optional | human-readable summary shown in `pgserve trust list` |
| `addedAt` | populated by `pgserve trust add` | ISO-8601 timestamp |

**Do not edit this file by hand.** The verbs ensure schema validity, mode bits,
and audit logging. A malformed file causes `pgserve trust list` to exit code
2 ("trust store on disk is malformed and must be repaired by hand").

## CLI reference

### `pgserve trust list`

Prints the union of hardcoded + user entries. Hardcoded entries are marked
`source=hardcoded removable=false`; user entries are `source=user
removable=true`.

```bash
pgserve trust list           # human-readable table
pgserve trust list --json    # JSON array of entries
```

Exit codes:
- `0` — list printed
- `2` — user trust file malformed

### `pgserve trust add <id> --issuer <url> --identity-regexp <re> [--publisher <name>] [--description <text>]`

Adds a new entry to `~/.pgserve/trust/identities.json`. All flags except
`--publisher` and `--description` are required.

```bash
pgserve trust add my-org-release \
    --issuer https://token.actions.githubusercontent.com \
    --identity-regexp '^https://github.com/my-org/cli/.github/workflows/release.yml@refs/tags/v.*$' \
    --publisher '@my-org/cli' \
    --description 'My private release pipeline'
```

Exit codes:
- `0` — entry written
- `1` — bad flags, missing required, or `<id>` collides with a hardcoded entry

### `pgserve trust remove <id>`

Removes a user entry. Refuses to remove hardcoded ids.

```bash
pgserve trust remove my-org-release
```

Exit codes:
- `0` — entry removed
- `1` — unknown id, or `<id>` matches a hardcoded entry

## Precedence rules

1. A binary verifies if **any** hardcoded OR user entry matches its cosign
   attestation. There is no override; both layers grant trust.
2. `pgserve create-app <slug>` snapshots the **union** of hardcoded + user
   entries into `autopg_meta.locked_roots` at the moment of creation. After
   create-app, `pgserve verify --slug <slug>` consults only that frozen
   snapshot — adding/removing user trust **after** create-app does NOT affect
   what an already-locked slug accepts.
3. To rotate trust for a locked slug, the operator must `rm -rf
   ~/.autopg/<slug>/` and re-run `pgserve create-app <slug>` to recapture the
   current trust list. (See [`docs/pgserve-meta.md`](pgserve-meta.md) for the
   source-of-truth split between `autopg_meta` and the cache files.)

## Doctor checks

`pgserve doctor` currently does **not** probe the trust store. The supervisor,
postmaster, pm2 wiring, and `~/.autopg/admin.json` shape are what doctor
inspects today (see `src/commands/doctor.js`). Trust-store integrity checks
(file modes, schema validity, publisher-match) are reserved for a future
release — tracked under `pgserve-singleton-no-proxy` Group 6 (self-healing
`pgserve update` pipeline) and its companion `doctor --fix` tiered modes.

Until those land, operators verify the trust store manually:

```bash
# Inspect the user-extensible store (JSON list)
pgserve trust list --json | jq

# Confirm hardcoded entries are present (regression sanity)
pgserve trust list --json | jq '[.[] | select(.source == "hardcoded")] | length'
# Expected: >= 3 (genie, omni, pgserve self-trust)

# Confirm file mode is 0600 (manual check)
stat -c '%a' ~/.pgserve/trust/identities.json 2>/dev/null || stat -f '%Lp' ~/.pgserve/trust/identities.json
# Expected: 600
```

## Audit

`pgserve trust add` and `pgserve trust remove` currently do **not** write
a dedicated audit log. The user-extensible store at
`~/.pgserve/trust/identities.json` is the audit trail itself: each entry
carries an `addedAt` ISO-8601 timestamp populated by `validateEntry()` in
`src/cosign/trust-store.js`. Removed entries are dropped without a tombstone.

A dedicated `~/.pgserve/audit/trust-<DATE>.log` analogue to the `gc` audit
log is tracked as a future enhancement under `pgserve-singleton-no-proxy`
(no shipped wish today). Operators who need a separate trust-mutation
audit log can wrap the verb in their own shell history capture until then.
